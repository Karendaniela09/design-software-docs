# Decisiones internas — document-service

estado 🟢 Estable — 2026-10-24

> Para decisiones que afectan más de un servicio → crear ADR en `05-architecture/decisions/records/`
> Ver ADR-003 (estrategia de almacenamiento de documentos)

| # | Decisión | Alternativas descartadas | Motivo | Fecha |
|---|----------|--------------------------|--------|-------|
| 01 | Binarios en object storage únicamente; `document_db` almacena solo metadatos | Guardar archivos en BD como `bytea` o `BLOB` | Object storage es más barato, más eficiente para archivos grandes y habilita pre-signed URLs y distribución CDN; los binarios en BD inflan los backups, degradan el rendimiento de las queries sobre metadatos y no permiten streaming parcial | 2026-06-17 |
| 02 | Generación de PDF es asíncrona mediante `pdf-renderer-worker` + cola | Generación síncrona en el endpoint REST | El renderizado de PDF (HTML→PDF via headless browser o librería) puede superar 2 segundos; una respuesta síncrona bloquearía la conexión del cliente y excedería timeouts de API gateway; el patrón worker + cola permite reintentos, backpressure y paralelismo controlado | 2026-06-17 |
| 03 | `document_version` para historial; la versión actual es `document.storage_key` (sin `current_version_id` separado) | Mantener un campo `current_version_id` con FK a `document_version` | Un `current_version_id` requeriría un JOIN adicional en cada lectura de documento; `document.storage_key` apunta siempre a la versión activa directamente; el historial completo sigue disponible en `document_version` para quien lo necesite | 2026-06-20 |
| 04 | Sistema de plantillas HTML/Handlebars; no PDFs hardcodeados | Plantillas hardcodeadas como archivos PDF estáticos o código Java/Node que genera el layout | Las plantillas HTML/Handlebars permiten que usuarios no técnicos editen el contenido y la estructura desde la interfaz de administración; los PDFs estáticos no son parametrizables; el código de layout mezclado con la lógica de negocio hace que cada cambio de formato requiera un deploy | 2026-06-20 |
| 05 | Dos proveedores de storage (MinIO en desarrollo, S3 en producción) mediante patrón adapter (ADR-003) | Un único proveedor en todos los entornos | MinIO permite desarrollo y pruebas sin costo ni acceso a AWS; el adapter pattern garantiza que el código de negocio no dependa del proveedor concreto; cambiar de proveedor o agregar uno nuevo (Azure Blob, GCS) requiere solo implementar la interfaz, no modificar la lógica de servicio | 2026-06-20 |
| 06 | `document-mfe` (front end): el estado vive en hooks de React por caso de uso (`useDocuments`, `useDocumentVersions`, `useDocumentTemplates`, `useGenerateDocument`, `useUpdateTemplateState`) sobre puertos de salida (`DocumentRepository`, `TemplateRepository`, `HttpClientPort`, `AuthPort`); los repositorios se crean una sola vez por cliente inyectado en `App.tsx`; el detalle descarta respuestas obsoletas (`requestId`); los filtros de plantilla y fecha, que el contrato no soporta, se aplican en el cliente sobre la página recibida y con un debounce de 200 ms | Store global (Redux, Zustand); TanStack Query / SWR; `fetch` dentro de los componentes; contexto de permisos propio | El estado es de servidor y de alcance local a la vista, así que un store global solo duplicaría datos que el shell no comparte; los puertos permiten probar las vistas sin backend y cambiar la implementación sin tocar las vistas. TanStack Query es la opción natural si varias vistas llegan a compartir los mismos datos | 2026-10-24 |
| 07 | `document-mfe`: un fallo viaja hasta la vista junto a los datos anteriores y se muestra con la acción **Reintentar**; si falla el historial de versiones se muestra el error, nunca una lista vacía; si falla la consulta de plantillas que resuelve el código visible de cada documento, la tabla degrada a `—` y no queda vacía | Sustituir los datos por una lista vacía ante un error; romper el listado cuando falla la API de plantillas | Una lista vacía por un error es información falsa (regresión detectada por QA en HU-DOC-007); la tabla de documentos debe sobrevivir a una dependencia secundaria caída | 2026-10-24 |
| 08 | `document-mfe` no hace login, no lee ni guarda el token y no define su propio cliente HTTP: usa el `httpClient` autenticado que el shell le inyecta por `remote-props` ([ADR-023](../../../05-architecture/decisions/records/ADR-023-web-shell-owns-login-and-session.md)) y llama a la base relativa `/document/api/v1` por el edge ([ADR-022](../../../05-architecture/decisions/records/ADR-022-edge-routing-table-by-domain.md)); las plantillas (`/document-templates`) cuelgan de la misma base y el edge las lleva a `template-api` | Un shim local que lee `sessionStorage` y arma su `fetch`; una base por ambiente (`VITE_DOCUMENT_API_BASE_URL`); modo mock por variable de entorno | El token no se reparte por nueve repositorios y el artefacto es el mismo en los cuatro ambientes. Sin cliente inyectado el remote pide al shell que lo proporcione en vez de caer a datos locales; los datos en memoria solo existen en `npm run dev` | 2026-10-24 |
| 09 | `document-mfe`: los permisos de la UI salen de `permissions` (códigos de feature de la sesión sin sufijo de alcance) y `can(feature)` solo oculta o deshabilita acciones con un aviso visible; el backend es la autoridad, un `403` llega a la vista como error con el mensaje del cliente del shell, nunca como lista vacía, y un `401` lo resuelve ese cliente (un refresh y, si falla, `/login`) | Decodificar el JWT en el remote; un contexto de permisos propio; decidir permisos en el cliente | Decodificar el token en el remote lo expone y duplica la fuente de verdad de los permisos; la UI no puede ser la barrera de seguridad | 2026-10-24 |
